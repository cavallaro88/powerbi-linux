# Implementation validation — updated 2026-10-13

This is a development preview for Fedora 44 x86_64 on native Wayland. The existing investigation remains separate from the standalone project tree. Runtime imports and disposable copies of prepared prefixes are developer experiments, not proof that setup works from official installers.

The CLI has 23 passing unit tests covering private XDG state, maintenance locks, filenames with spaces/Unicode/shell characters, supported extensions, unsafe archives, runtime tampering, interrupted setup, failed update activation, rollback, production diagnostic isolation, session ownership, restoration of file associations and rejection of an unvalidated WebView2 update. The source-export test also verifies that model caches, environment files, keys and compiled binaries cannot leak from a fixture directory into the public project export. Production C# helpers compile; malformed inputs and the wrong assembly fail without creating an output. The desktop entry passes `desktop-file-validate`.

Pinned Wine/DXVK source preparation applies the patch series with zero fuzz. A reverse dry run also verified that the prepared sources contain the published patches. A compiler change exposed stale SymCrypt objects: those objects and their consumers were rebuilt with LLVM 19. The recipe now records the toolchain and refuses to mix compiler versions. Wine, WoW64, DXVK and the production helpers built successfully. The RPM and source RPM built successfully; the extracted RPM launcher and desktop entry passed their checks.

The earlier rebuilt runtime archive was `powerbi-linux-runtime-0.1.0-x86_64.tar.xz`, SHA-256 `28a5bd82d387fc11819a6e808a583af28125be0ccf207b8aca35ef5bc57a2f48`. Archive extraction and manifest integrity checks passed. Using this runtime and its new DXVK/production helpers in a disposable imported prefix, a cached synthetic PBIP displayed Cafe 120, Suco 100 and Cha 80, with Total 300; DAX independently confirmed 300. This validates a rebuilt runtime against prepared application state, not clean provisioning.

The same rebuilt runtime opened a synthetic PBIX with spaces and accents in its filename and directly opened `Synthetic.Report/definition.pbir`, resolving its relative semantic-model reference. Both displayed the expected total and passed the independent DAX check. These were CLI opens; file-manager association certification remains pending. All named RPM dependencies resolved in Fedora 44 repository queries, including the versioned Wayland and unixODBC libraries. This does not replace an actual DNF installation test.

In a disposable imported installation, the synthetic PBIX displayed Cafe 120, Suco 100 and Cha 80, with Total 300; an independent DAX query confirmed 300. Later opens lost the WebView page even with the original helper. Replacing the disposable WebView user-data directories restored a responding interface and the same visual values. This is an observation about test state; it does not establish a universal fix or justify deleting user profiles during normal launch.

Generated PBIP/TMDL fixtures initially contained definitions and queries without `.pbi/cache.abf`. They loaded table metadata, but their imported data was empty before refresh. That is expected: Microsoft's [semantic-model project documentation](https://learn.microsoft.com/en-us/power-bi/developer/projects/projects-dataset) describes `cache.abf` as an Analysis Services backup containing the model and locally loaded data. It is separate from this project's PE loader cache. Missing data must not be classified as a renderer failure.

An ordinary AMO backup request was rejected by Desktop's diskless Analysis Services instance. A populated synthetic PBIX was instead saved as PBIP using Desktop, producing its own cache. Two copies differed only by removal of `.pbi/cache.abf`: with it, the visual displayed total 300 and DAX confirmed 300; without it, the table metadata loaded and the same DAX sum was blank, as expected before refresh. Both tests completed their backend evidence checks. These binary model caches remain local and excluded from source exports. They do not certify a large-model UI refresh.

A generated 158-table PBIP was refreshed using Desktop's **Refresh → Schema and data** with the rebuilt runtime, a 10 GiB RAM / 4 GiB swap service limit and a 512 MiB V8 heap. All 157 fact tables contained the expected 10,000 rows, independently checked with DAX, and the sales visual displayed Total 300. The five-minute session sampled no cgroup OOM events, with approximately 9.01 GiB peak RAM. Desktop saved the project and generated its own local cache. A fresh reopen preserved all fact row counts and the visible sales total, without requesting another refresh. The fixture includes its own minimal theme and consistent report/visual identifiers; earlier incomplete fixtures must not be used to infer a product failure. This synthetic workload has no relationships or enterprise sources and does not reproduce every property of the original large report.

## Resumed validation — 2026-10-13

Production desktop dispatch through GIO passed for PBIX, PBIP and PBIR, including spaces/accents and relative project references. Two PBIX documents remained open together, with independently verified totals and responsive native windows; peak RAM was approximately 7.86 GiB, without OOM. The harness confirmed diagnostics and remote debugging were disabled. This tests desktop dispatch from the developer checkout; the system RPM is not installed on the native host.

Native lifecycle checks rejected an invalid checksum without pointer changes, repaired deliberately invalid derived-cache metadata, opened the repaired profile, updated to a verified candidate runtime, opened that generation and rolled back to the original installation. A unit regression additionally verifies that an installed system RPM entry is masked for the user and restored by integration without modifying system files.

A fresh native wineboot and explicit disabled-builder invocation produced no extra desktop/MIME entries. The regression suite now has 23 passing tests.
